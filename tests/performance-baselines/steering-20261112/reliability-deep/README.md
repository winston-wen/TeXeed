# 实际指针压力的交错复测（2026-11-12）

目的：定位 `--ai-reliability-only` 的真实系统指针移动未满足 500 ms 限制的原因。整个过程使用独立 `TEXEED_HOME`、合成文档，同一台 Windows 主机、.NET SDK 10.0.203，820×900 DIP WPF 测试窗口。没有改动 500 ms 阈值。每批测试在首个失败处结束，因此通过批次有 25 次指针样本，失败批次只有失败之前的样本；不能把它们直接平均比较。

## 第一轮：分阶段计时

对旧版 8b91463、功能构建、新版仅恢复旧 Cascadia 字体三个隔离源码副本，在相同的 25 次 `SetCursorPos` 循环中增加三次记录：同步调用返回、`Task.Delay(16)` 的 UI 线程延续恢复、`Dispatcher.Yield(Background)` 完成。记录耗时后才输出，不改变失败阈值。独占桌面，按旧、新、旧字体、新、旧、旧字体交错；每版两批，逐次日志为 `old-*.log.txt`、`new-*.log.txt`、`font-*.log.txt`。

| 构建 | 两批结果 | 失败时 set／延续恢复／最终耗时 |
| --- | --- | --- |
| 8b91463 | 通过／通过 | 无 |
| 新版 | 失败／失败 | 0.034／340.7／584 ms；0.028／270.2／562 ms |
| 新版、旧字体 | 通过／失败 | 0.035／509.2／509 ms |

同步 `SetCursorPos` 开销很小；主要等待发生在定时任务的 UI 延续恢复之前，或后续 Background 队列中。`Task.Delay` 返回时刻本身包含计时器和 UI 线程调度，不能据此单独归因操作系统定时器或 WPF。旧字体仍可失败，单次通过也不能证明它无成本；两个版本各两批不足以确定故障概率。

## 第二轮：Dispatcher 操作与反事实

在同一循环有限时间内附加 Dispatcher OperationStarted／OperationCompleted 钩子，记录至少 8 ms 的操作优先级、回调类型和从开始到完成的耗时，不记录文档内容。钩子包含反射与计时，因此存在观察开销，结果不能与第一轮的不带 Dispatcher 钩子的通过率直接比较。按旧、新、移除按钮、旧状态灯、旧字体、旧字体、旧状态灯、移除按钮、新、旧交错，每版两批；逐次日志为 `dispatcher-*.log.txt`。

| 构建 | 两批结果 | 每批最长 WPF Render 操作 |
| --- | --- | --- |
| 8b91463 | 失败／失败 | 268.5／261.0 ms |
| 新版 | 失败／失败 | 303.5／272.8 ms |
| 新版、移除两个按钮 | 失败／通过 | 321.4／284.1 ms |
| 新版、旧状态灯 | 失败／失败 | 273.5／304.6 ms |
| 新版、旧字体 | 失败／失败 | 267.3／269.4 ms |

长操作主要为 Render 优先级的 `System.Windows.Media.MediaContext.RenderMessageHandler`，并观察到 Background 优先级的 `MarkdownView.RenderDeferredAsync`。较高优先级渲染操作可在等待期间连续运行，但钩子没有分配调用栈或布局子树，不能将全部开销归因于某个具体控件。旧版在插桩下也超时，说明历史版本存在长渲染队列；去掉单项功能未稳定消除超时，尚不能把新版失败归因于字体、按钮或状态灯，也不能据此宣称完全没有新版本退化。压力测试性能验收没有通过。

移除按钮的构建从视觉树中删除两个按钮，保留脱离视觉树的同名空按钮以满足宿主字段；旧状态灯使用 8b91463 实现并保留仅用于编译测试的兼容构造器；旧字体将应用编辑字体回到 Cascadia 且常规字重。精确修改见各 `.patch`，测试源码为 `fixture-old-instrumented.cs.txt` 和 `fixture-new-instrumented.cs.txt`。按钮反事实改变布局，不能把差异全部认作按钮自身成本。版本构建冻结后又修复了首轮 checkpoint 保存期间引用编辑的清理竞态，该修改与此静态阅读布局无关；正式发布程序集没有测量。
