# 附件上传与路径引用性能（2026-11-11）

比较改前提交 `1430ab2` 与本次功能构建。使用合成的资料及隔离的 `TEXEED_HOME`，不访问真实会话。测量只覆盖显示操作，不调用真实 AI，也未测真实文件目录搜索、上传网络或最终发布二进制。

## 浏览器原型

`prototype.cjs` 用 Chrome 157，1000×820 视口、120 轮对话，包含一条引用和一个附件目录。目录分别使用 31 个文件的旧快照，以及单条目录路径引用；加号菜单和输入 `@` 分别测量。旧版输入 `@` 没有路径候选，新版显示三个示例候选。先运行旧版再运行新版，每个场景预热 2 次，记录 7 次工作与空操作配对，等待两帧及 220 ms，CDP 采样分配间隔 1024 B。基线和功能版资源 SHA-256 与原始样本见 `prototype-results.json`。

| 场景 | 同步中位旧／新 | 校正采样旧／新 | 可见控件旧／新 |
| --- | --- | --- | --- |
| 打开 31 文件旧快照目录附件列表 | 2.7／2.4 ms | 23,884／22,808 B | 15／15 |
| 打开一条目录路径引用的附件列表 | 2.4／2.5 ms | 2,092／4,524 B | 15／15 |
| 打开加号菜单 | 0.1／0 ms | −1,092／1,008 B | 15／16 |
| 输入 `@` | 0.1／0.2 ms | 14,540／16,196 B | 13／16 |

加号菜单新增一项，控件增加 1 个；`@` 候选新增三个控件。每版仅一批，校正耗时和采样中出现负值，不能据此推断小幅耗时或分配差异。历史可复核的旧快照长目录附件列表候选同步中位 3.9 ms／19,732 B、15 个可见控件，见 `../folder-slash-20261111/prototype-folder.json`；其功能版本、计时条件及采样波动仍需一并考虑。目录路径引用、菜单和 `@` 候选此前没有完全相同的历史场景。

复测时设置 `TEXEED_PLAYWRIGHT_PATH` 指向 Playwright 包，`TEXEED_BROWSER_PATH` 指向 Chrome，然后在仓库根执行 `node tests/performance-baselines/claude-attachments-20261111/prototype.cjs`。脚本从固定提交 `1430ab2` 提取旧版原型，结果写入 `artifacts/claude-attachments-perf-20261111/prototype/`。

### 图片缩略图

`image-list-fixture.cs.txt` 在相同目录弹窗中添加 256×256 PNG，等待 `AttachmentThumbnail.LoadTask` 和后续 UI 队列排空；按旧、新、新、旧各两批、2 次预热及 7 次采样。旧／新打开弹窗的 UI 线程分配为 38,984／171,672 B，耗时为 6.76–7.73／17.19–18.12 ms，弹窗 WPF 控件均 9，但新版本显示 1 张图片、旧版无图片。`image-tiny-fixture.cs.txt` 的 1×1 有效图得到相近分配 38,992／171,688 B；`image-invalid-fixture.cs.txt` 中新版本解码失败不显示图片时为 41,296 B。有效图成功显示和布局相比失败路径约多 130 KB；未采调用栈，不能断言这全部是不可避免的实现成本，后台解码线程分配也没有计入。图片结果见 `results-deep-image-*`、`results-isolated-image-tiny-*`、`results-isolated-image-invalid-*`。图像功能构建未包含后续历史上下文重放，不能直接外推到大图、大批图片或发布后的真实工作负载。

`run-native.ps1`、`run-deep.ps1` 和 `run-isolated.ps1` 记录执行顺序。复测需先依据源码夹具编译名为 Runner 的独立 WinExe（参考 `image-runner.csproj.txt`，将夹具复制为 Program.cs 并传入 `TeXeedReferenceDir`），并将隔离构建及 Runner 放入脚本所指的 `artifacts/claude-attachments-perf-20261111/`；`build-isolated.ps1` 可从相同工作树生成候选复用单变量构建。临时构建和实际运行输出均在 `artifacts/`，不写入真实资料。
