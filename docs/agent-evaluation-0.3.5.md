# TeXeed 0.3.5：AI 工作助手验收记录

评估日期：2026-10-13（北京时间）。所有文档实验均在用户授权项目的独立副本中进行，使用 Git 快照保留初始状态；未在原始书籍或笔记目录应用模型修改。测试副本、模型原始输出和编译产物不进入源码提交。

## 本次解决的问题

首条有效问题提交时立即显示并保存会话标题，不再等待模型结束。慢响应、取消和失败均覆盖，已有自定义标题保持不变。

原工具只能看到主文件依赖图，未引用模板和构建资料没有进入模型视野。本版提供有界的工作区目录预览，以及目录分页、未引用文件读取和全文检索。`.latexmkrc`、`.vscode/settings.json`、`.vscode/tasks.json` 和指定构建脚本可只读检查；其他隐藏路径继续拒绝访问。脚本不执行。

工作提示词集中在源码 `src/TeXeed.App/AI/AiAgentPrompt.cs`，发行包也提供相同内容的 [AI 工作规则](agent-instructions.md)。它规定先查入口与项目约定、复用已有定义、精确修改、保留正文、实际编译、继续处理真实错误，并如实区分缺失源码、环境问题和未验证结果。最终答复概述修改与证据，不要求用户复制源码。提示词是本项目编写的工作规则，不是提取其他产品的内部提示词。

配套能力包括：指定已有包装入口进行编译；明确实际验证范围；按入口隔离输出缓存；使预览与实际编译入口关联；保留备份、撤销及冲突检查。流式输出按消息补齐终态，避免部分工具或最终回复被遗漏。超长旧回答不会使最近用户约束整轮消失。

子目录入口按自身目录解析模板和相对路径。真实测试覆盖中文及带空格目录、根目录与子目录的同名模板、父目录正文、BibTeX/Biber 文献库，以及原生和命令行 SyncTeX。编译途中输入发生变化、文件监视器溢出或正文未载入，都不能再被当作当前有效的成功结果。

## 真实模型与原项目副本

Sol 使用 `gpt-6.1-sol`，推理强度始终为 `low`（轻）。DeepSeek 使用 `deepseek-flash`。TeXeed 走 Responses 接口，本机 Claude Code 对照走 DeepSeek 的 Anthropic 兼容接口；通道与工具集不同，不能把差异全部归因于提示词。

共享请求总账最终为 **Sol 34 / 200、DeepSeek 59 / 500**，DeepSeek 数字包含 Claude Code 对照的 13 次请求。未耗尽授权额度，也未按余额推算费用。

| --- | ---: | ---: | --- |

| 《康熙的红票》，左右页边距改为 22mm | 5 | 4 | 仅改变共享定义中两个数值；313 页 PDF 编译通过，全部页面仍为 176×250mm |

| DKLS，干净副本上的“编译不过，帮我修” | 3 | — | 实际尝试编译；报告所需字体和 14 篇正文片段缺失；保留源码，不伪造章节或以换字体掩盖问题 |

正文验收不只依赖模型自述：比较测试前后的全部源码清单与 SHA-256，再将被允许修改的文件与明确的预期内容逐字比较。Fraleigh 的错误修复必须恢复原始内容；页边距只能替换两个数值；评论框只能替换背景值。页面数与纸张大小另从实际编译产物的逐页布局记录核对。

包装场景使用自行编写的短片段，不把它描述为原书已有故障。验收要求编译正确的包装入口，并保留默认片段入口；编译任意其他文件不能通过 `--require-compile` 的入口检查。

### 保留的失败与迭代

- 首轮 DKLS 修复使用了 6 次 Sol 请求。模型主动检查了构建资料，也准确报告缺失正文，但在此之前给主模板增加了字体回退。这个用例的“主模板保持原样”检查失败；编译也未成功。该记录保留，未并入成功案例。随后明确区分环境阻碍与源码修复，从干净副本重测，模型保留了主模板并报告具体阻碍。
- DeepSeek 的早期答复曾在没有改前编译基线时称警告“既存”，以及只读取样式前段却称“读完”。工作规则已补充证据范围要求。重复页边距案例中修改与编译仍正确，但模型再次把警告称为“本就存在”，该例的最终措辞准确性未通过；因此编译工具也直接标明诊断只代表本次输出，不包含前后比较。
- 第一轮 DeepSeek 包装案例操作正确，但最终答复附带了整份短包装源码。收紧收尾规则后的重复案例使用 5 次请求，正确编译指定入口，最终只概述修改与验证，没有代码块。
- 只读调查中曾把未引用文件称为“旧稿”，并对“唯一入口”作过强判断。规则已明确：未被当前入口引用不能证明废弃或不可独立编译。

最后一轮 Sol 只读调查使用 3 次请求，读到模板、包装脚本和编辑器构建配置，正确区分当前入口、独立模板与构建约定，未再次断言未引用文件已废弃。

最终代码构建后再从干净副本复测：Sol 使用 4 次请求修复 Fraleigh 第 6 章，内容逐字恢复原始文件并编译为 13 页；DeepSeek 使用 5 次请求完成全书左右边距修改，只改变两个数值，313 页全部保持 B5。加入工具诊断范围说明后，这次最终回复没有再次将警告断言为原有或与修改无关。这是一个通过的重复样本，早先的失败记录仍保留。

这些测试证明了所列场景的实际表现，不证明任何模型在所有 TeX 项目上的可靠性或与 Claude Code 全面等价。缺失正文、未安装字体、任意外部命令执行和复杂版面目视判断仍有能力边界。

另保留编译引擎自身的限制：Tectonic 的受限模式不支持依赖 `TEXINPUTS` 的项目根目录搜索回退；TeX Live 会拒绝 `\include{../...}` 写出父目录辅助文件。此时需按实际构建约定选择入口、相对 `\input` 路径或引擎。程序不会放宽引擎限制，也不会用缺少正文的 PDF 覆盖上一份完整结果。

## Claude Code 同题对照

使用本机 VS Code 插件附带的 Claude Code 2.1.296，在同一个 DKLS 副本上执行只读调查，用了 13 次 DeepSeek 请求。它沿 README、Makefile、包装脚本和编辑器设置找出了构建链，并报告正文缺失。这个对照促使本版补齐未引用文件和编辑器构建配置的可见性。

对照仅允许 `Read`、`Glob`、`Grep`，使用 `--restricted` 限定工作目录；没有执行 shell 或编辑原始项目。它验证的是发现与诊断，不是编辑和编译能力的对等证明。脚本在启动前核验本机 CLI 的受限模式说明，关闭额外工具连接，并对日志统一脱敏。

## 可重复运行的验证工具

普通测试不调用真实模型。付费测试必须显式指定 `--ai-live-agent`，入口旁必须存在 `.texeed-evaluation-copy` 标记，并使用隔离配置目录。示例：

```powershell
dotnet run --project tests/TeXeed.AppTests -c Release --no-build -- `
  --ai-live-agent --provider sol --project <副本入口.tex> `
  --profile <隔离配置目录> --output <全新的结果目录> `
  --ledger <共享预算.json> --prompt-file <问题.txt> `
  --engine XeLaTeX --engine-path <xelatex.exe> `
  --require-compile --only-change <允许修改的文件>
```

包装测试还应指定 `--expected-entry <包装入口.tex>`。可追加 `--must-read`、`--must-preserve`、`--must-change`、`--must-use-tool` 或 `--read-only`。允许修改文件的具体内容仍需按用例做独立差异验收。

每次模型 HTTP 请求在发送前写入共享总账，失败请求也计数；Sol 上限 200，DeepSeek 上限 500。Node 与 .NET 测试共用独占账本锁。应用不会自动运行这些付费用例，也不会读取 Claude 配置；DeepSeek 配置适配仅在测试工程与对照脚本中存在。

TeXeed 应用评测每例输出 `result.json`、`events.jsonl`、`answer.md`、修改前后 SHA-256 清单；Claude CLI 对照输出过程、结果和答复，不生成这两份清单。包含用户文档片段的本机日志与副本留在忽略目录中，不随发行包发布。纯离线的评估工具自身有 12 项入口验收检查与 19 项凭据脱敏、预算等检查。
